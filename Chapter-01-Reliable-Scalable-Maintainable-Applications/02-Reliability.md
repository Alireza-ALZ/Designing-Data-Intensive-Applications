# Chapter 1 — Reliable, Scalable, and Maintainable Applications

## Reliability

همهٔ ما درک شهودی‌ای از معنای reliable یا unreliable بودن یک چیز داریم. دربارهٔ software، انتظارهای معمول شامل موارد زیر است:

- application همان functionای را اجرا کند که کاربر انتظار دارد.
- بتواند اشتباه‌های کاربر یا استفادهٔ غیرمنتظره از software را تحمل کند.
- performance آن، با توجه به `use case` موردنیاز و `load` و حجم دادهٔ مورد انتظار، به‌اندازهٔ کافی خوب باشد.
- سیستم از هرگونه دسترسی غیرمجاز و سوءاستفاده جلوگیری کند.

اگر مجموع این موارد را «درست کار کردن» بدانیم، می‌توانیم reliability را به‌طور تقریبی این‌گونه تعریف کنیم: «ادامه دادن به کارکرد صحیح، حتی وقتی چیزهایی خراب می‌شوند.»

به چیزهایی که ممکن است خراب شوند `fault` می‌گوییم و سیستم‌هایی را که faultها را پیش‌بینی می‌کنند و می‌توانند با آن‌ها مقابله کنند، `fault-tolerant` یا `resilient` می‌نامیم. عبارت اول کمی گمراه‌کننده است، چون این تصور را ایجاد می‌کند که می‌توانیم سیستم را در برابر هر نوع fault ممکن مقاوم کنیم؛ در حالی که در واقع چنین چیزی شدنی نیست. اگر تمام سیارهٔ زمین، همراه با همهٔ serverهای روی آن، توسط یک سیاه‌چاله بلعیده شود، تحمل چنین faultی به `web hosting` در فضا نیاز خواهد داشت - موفق باشید که تصویب چنین ردیفی را در بودجه بگنجانید! بنابراین فقط صحبت کردن از تحمل انواع مشخصی از fault معنا دارد.

توجه کنید که `fault` با `failure` یکی نیست [2]. معمولاً fault را این‌گونه تعریف می‌کنند: یکی از componentهای سیستم از `spec` خود منحرف شود؛ در حالی که failure زمانی رخ می‌دهد که کل سیستم دیگر service موردنیاز کاربر را ارائه نکند. صفر کردن احتمال وقوع fault غیرممکن است؛ بنابراین معمولاً بهتر است مکانیزم‌های `fault tolerance` را طوری طراحی کنیم که مانع تبدیل faultها به failure شوند. در این کتاب، چندین تکنیک برای ساختن سیستم‌های reliable از اجزای unreliable بررسی می‌کنیم.

برخلاف شهود اولیه، در چنین سیستم‌های fault-tolerantای گاهی منطقی است که نرخ وقوع fault را با ایجاد عمدی آن‌ها افزایش دهیم؛ برای مثال، می‌توانیم processهای منفرد را به‌صورت تصادفی و بدون هشدار متوقف کنیم. بسیاری از bugهای مهم در واقع نتیجهٔ `error handling` ضعیف‌اند [3]. با ایجاد عمدی fault، مطمئن می‌شویم که machinery مربوط به fault tolerance به‌طور مداوم اجرا و آزمایش می‌شود؛ این کار می‌تواند اعتماد ما را افزایش دهد که وقتی faultها به‌صورت طبیعی رخ می‌دهند، درست مدیریت خواهند شد. `Netflix Chaos Monkey` نمونه‌ای از این رویکرد است.

هرچند معمولاً ترجیح می‌دهیم faultها را تحمل کنیم تا اینکه از وقوع آن‌ها جلوگیری کنیم، در بعضی موارد پیشگیری بهتر از درمان است؛ برای مثال، وقتی درمانی وجود ندارد. مسائل امنیتی نمونه‌ای از همین حالت‌اند: اگر یک attacker سیستمی را compromise کرده و به داده‌های حساس دسترسی پیدا کرده باشد، نمی‌توان آن رویداد را به حالت قبل برگرداند. با این حال، این کتاب عمدتاً با faultهایی سروکار دارد که قابل درمان‌اند؛ همان‌طور که در بخش‌های بعدی توضیح داده می‌شود.

### Hardware Faults

وقتی به علت‌های system failure فکر می‌کنیم، `hardware fault`ها خیلی زود به ذهن می‌رسند. hard diskها crash می‌کنند، RAM خراب می‌شود، شبکهٔ برق دچار blackout می‌شود و ممکن است کسی کابل شبکهٔ اشتباهی را از برق بکشد. هرکس با datacenterهای بزرگ کار کرده باشد می‌تواند به شما بگوید که وقتی تعداد زیادی machine دارید، این اتفاق‌ها همیشه رخ می‌دهند.

گزارش شده است که `hard disk`ها `mean time to failure (MTTF)`ای حدود ۱۰ تا ۵۰ سال دارند [5, 6]. بنابراین در یک storage cluster با ۱۰٬۰۰۰ disk، به‌طور میانگین باید انتظار داشته باشیم هر روز یک disk از کار بیفتد.

واکنش اولیهٔ ما معمولاً این است که با افزودن `redundancy` به componentهای سخت‌افزاری منفرد، نرخ failure سیستم را کاهش دهیم. diskها ممکن است در یک پیکربندی `RAID` قرار بگیرند، serverها ممکن است دو منبع تغذیه و CPUهای `hot-swappable` داشته باشند و datacenterها ممکن است برای برق پشتیبان به باتری و generatorهای دیزلی مجهز شوند. وقتی یک component از کار می‌افتد، component redundant می‌تواند جای آن را بگیرد تا component خراب تعویض شود. این رویکرد نمی‌تواند به‌طور کامل مانع تبدیل مشکلات سخت‌افزاری به failure شود، اما روشی شناخته‌شده است و اغلب می‌تواند یک machine را سال‌ها بدون interruption روشن نگه دارد.

تا همین اواخر، `hardware redundancy` برای بیشتر applicationها کافی بود، چون احتمال failure کامل یک machine منفرد را بسیار کم می‌کند. تا وقتی بتوانید یک backup را نسبتاً سریع روی machine جدید restore کنید، downtime ناشی از failure در بیشتر applicationها فاجعه‌بار نیست. بنابراین `multi-machine redundancy` فقط برای تعداد کمی از applicationها لازم بود که `high availability` برایشان کاملاً حیاتی بود.

با افزایش حجم داده و نیازهای محاسباتی applicationها، applicationهای بیشتری شروع به استفاده از تعداد بزرگ‌تری machine کردند؛ این موضوع به‌طور متناسب نرخ hardware faultها را افزایش می‌دهد. علاوه بر این، در بعضی cloud platformها مانند `Amazon Web Services (AWS)` نسبتاً رایج است که `virtual machine instance`ها بدون هشدار از دسترس خارج شوند [7]، چون این platformها طوری طراحی شده‌اند که `flexibility` و `elasticity` را بر reliability یک machine منفرد ترجیح دهند.

در نتیجه، حرکت به سمت سیستم‌هایی شکل گرفته است که می‌توانند از دست رفتن کامل machineها را تحمل کنند؛ این کار با استفاده از تکنیک‌های `software fault tolerance`، به‌جای hardware redundancy یا در کنار آن، انجام می‌شود. چنین سیستم‌هایی از نظر operations نیز مزیت دارند: یک سیستم single-server اگر لازم باشد machine را reboot کنید - مثلاً برای نصب security patchهای operating system - به downtime برنامه‌ریزی‌شده نیاز دارد؛ اما سیستمی که failure یک machine را تحمل می‌کند، می‌تواند patchها را هر بار روی یک node اعمال کند، بدون اینکه کل سیستم دچار downtime شود. این فرایند `rolling upgrade` نام دارد.

### Software Errors

معمولاً hardware faultها را تصادفی و مستقل از یکدیگر می‌دانیم: خراب شدن disk یک machine به این معنا نیست که disk یک machine دیگر هم قرار است خراب شود. ممکن است هم‌بستگی‌های ضعیفی وجود داشته باشد - برای مثال، به‌دلیل یک علت مشترک مانند دمای rack سرورها - اما در حالت عادی بعید است تعداد زیادی از componentهای سخت‌افزاری هم‌زمان از کار بیفتند.

دستهٔ دیگری از faultها، `systematic error`های داخل سیستم هستند [8]. پیش‌بینی این faultها دشوارتر است و چون در nodeهای مختلف با یکدیگر هم‌بسته‌اند، معمولاً نسبت به hardware faultهای غیرهم‌بسته باعث failureهای بسیار بیشتری در سیستم می‌شوند [5]. نمونه‌ها عبارت‌اند از:

- یک `software bug` که باعث می‌شود هر instance از application server، هنگام دریافت یک input خاص و نامعتبر crash کند. برای مثال، `leap second` در ۳۰ ژوئن ۲۰۱۲ باعث شد بسیاری از applicationها به‌دلیل bug در `Linux kernel` به‌طور هم‌زمان hang کنند [9].
- یک `runaway process` که بخشی از resource مشترک را تمام می‌کند - مانند زمان CPU، memory، فضای disk یا پهنای باند network.
- سرویسی که سیستم به آن وابسته است و کند می‌شود، پاسخ نمی‌دهد یا شروع به برگرداندن responseهای خراب می‌کند.
- `cascading failure`، که در آن یک fault کوچک در یک component، faultی را در component دیگری ایجاد می‌کند و آن fault نیز به نوبهٔ خود faultهای بیشتری را به وجود می‌آورد [10].

باگ‌هایی که باعث چنین software faultهایی می‌شوند، اغلب برای مدت زیادی پنهان می‌مانند تا اینکه مجموعه‌ای غیرمعمول از شرایط آن‌ها را فعال کند. در چنین شرایطی مشخص می‌شود که software دربارهٔ محیط خود نوعی assumption داشته است؛ این assumption معمولاً درست است، اما سرانجام به دلیلی دیگر درست نخواهد بود [11].

برای مشکل systematic faultها در software راه‌حل سریع و ساده‌ای وجود ندارد. با این حال، کارهای کوچک زیادی می‌توانند کمک کنند: با دقت فکر کردن دربارهٔ assumptionها و interactionهای سیستم؛ `testing` کامل؛ `process isolation`؛ اجازه دادن به processها برای crash و restart؛ و اندازه‌گیری، monitoring و analysis رفتار سیستم در production. اگر انتظار می‌رود سیستم guarantee مشخصی ارائه دهد - برای مثال، در یک message queue تعداد messageهای ورودی با تعداد messageهای خروجی برابر باشد - سیستم می‌تواند در زمان اجرا دائماً خودش را بررسی کند و در صورت مشاهدهٔ discrepancy، alert ایجاد کند [12].

### Human Errors

انسان‌ها سیستم‌های software را طراحی و ساخته‌اند و operatorهایی که سیستم‌ها را روشن و در حال اجرا نگه می‌دارند نیز انسان هستند. حتی وقتی بهترین نیت را دارند، انسان‌ها به unreliable بودن معروف‌اند. برای مثال، یک مطالعه دربارهٔ serviceهای بزرگ اینترنتی نشان داد که `configuration error`های operatorها مهم‌ترین علت outageها بوده‌اند؛ در حالی که hardware faultها - در server یا network - فقط در ۱۰ تا ۲۵ درصد outageها نقش داشته‌اند [13].

چگونه می‌توانیم با وجود unreliable بودن انسان‌ها، سیستم‌های reliable بسازیم؟ بهترین سیستم‌ها چند رویکرد را با هم ترکیب می‌کنند:

- سیستم‌ها را طوری طراحی کنید که فرصت‌های خطا را به حداقل برسانند. برای مثال، abstractionها، APIها و admin interfaceهای خوب‌طراحی‌شده، انجام «کار درست» را آسان و انجام «کار اشتباه» را دشوار می‌کنند. با این حال، اگر interfaceها بیش از حد محدودکننده باشند، افراد راهی برای دور زدن آن‌ها پیدا می‌کنند و مزیتشان از بین می‌رود؛ بنابراین رسیدن به تعادل درست در اینجا دشوار است.
- محل‌هایی را که افراد بیشترین اشتباه را در آن‌ها مرتکب می‌شوند، از محل‌هایی که اشتباه می‌تواند باعث failure شود جدا کنید. به‌طور خاص، محیط‌های `sandbox` غیر-production و کاملاً مجهزی فراهم کنید تا افراد بتوانند با استفاده از دادهٔ واقعی، با خیال راحت در آن‌ها جست‌وجو و آزمایش کنند، بدون اینکه کاربران واقعی تحت تأثیر قرار بگیرند.
- در همهٔ سطح‌ها به‌طور کامل `test` کنید؛ از `unit test` گرفته تا `whole-system integration test` و testهای دستی [3]. `automated testing` به‌طور گسترده استفاده می‌شود، روش آن به‌خوبی شناخته شده است و برای پوشش دادن `corner case`هایی که در operation عادی به‌ندرت رخ می‌دهند، ارزش ویژه‌ای دارد.
- امکان `recovery` سریع و ساده از خطاهای انسانی را فراهم کنید تا در صورت وقوع failure، اثر آن به حداقل برسد. برای مثال، بازگرداندن `configuration change`ها را سریع کنید، code جدید را به‌تدریج `roll out` کنید تا bugهای پیش‌بینی‌نشده فقط بخش کوچکی از کاربران را تحت تأثیر قرار دهند و ابزارهایی برای محاسبهٔ دوبارهٔ داده فراهم کنید؛ چون ممکن است مشخص شود computation قبلی نادرست بوده است.
- `monitoring` دقیق و روشنی راه‌اندازی کنید؛ برای مثال، `performance metric`ها و `error rate`ها را اندازه بگیرید. در سایر شاخه‌های engineering به این کار `telemetry` گفته می‌شود. وقتی یک rocket زمین را ترک می‌کند، telemetry برای دنبال کردن اتفاق‌های در حال وقوع و فهمیدن failureها ضروری است [14]. monitoring می‌تواند سیگنال‌های هشدار اولیه را نشان دهد و به ما اجازه دهد بررسی کنیم آیا assumption یا constraintای نقض شده است یا نه. هنگام بروز مشکل، metricها برای تشخیص مسئله بسیار ارزشمندند.
- رویه‌های مدیریتی و training مناسبی اجرا کنید؛ این موضوع جنبه‌ای پیچیده و مهم دارد و خارج از scope این کتاب است.

### How Important Is Reliability?

Reliability فقط برای نیروگاه‌های هسته‌ای و software کنترل ترافیک هوایی نیست؛ از applicationهای معمولی‌تر نیز انتظار می‌رود reliable باشند. bugهای موجود در business applicationها باعث از دست رفتن productivity می‌شوند و اگر اعداد به‌اشتباه گزارش شوند، خطرهای حقوقی نیز ایجاد می‌کنند. outageهای سایت‌های ecommerce هم می‌توانند از نظر درآمد از دست‌رفته و آسیب به reputation، هزینه‌های بسیار سنگینی داشته باشند.

حتی در applicationهای «غیرحیاتی» نیز در برابر کاربران خود مسئولیت داریم. پدر یا مادری را در نظر بگیرید که همهٔ عکس‌ها و ویدئوهای فرزندانش را در photo application شما ذخیره کرده است [15]. اگر آن database ناگهان corrupt شود، چه احساسی خواهد داشت؟ آیا می‌داند چگونه آن را از روی backup restore کند؟

موقعیت‌هایی وجود دارد که ممکن است برای کاهش هزینهٔ development - مثلاً هنگام ساخت prototype محصولی برای بازاری که هنوز اعتبارسنجی نشده است - یا کاهش هزینهٔ operations - مثلاً برای سرویسی با profit margin بسیار کم - reliability را فدا کنیم؛ اما باید کاملاً آگاه باشیم که چه زمانی در حال حذف کردن گوشه‌های مهم کار و `cutting corners` هستیم.

## Key Terms

- `Reliability` — توانایی ادامهٔ عملکرد صحیح سیستم در شرایط نامساعد، حتی در برابر fault، failure و خطای انسانی.
- `Fault` — انحراف یک component از specification خود که ممکن است به failure کل سیستم منجر شود.
- `Failure` — از کار افتادن service در سطح کل سیستم و ناتوانی آن در ارائهٔ service موردنیاز کاربر.
- `Fault Tolerance` — مکانیزم‌ها و طراحی‌هایی برای جلوگیری از تبدیل faultهای اجزای unreliable به failure سیستم.
- `Fault-Tolerant` — صفت سیستمی که می‌تواند faultهای مشخصی را تحمل کند و service را ادامه دهد.
- `Resilient` — سیستمی که در برابر اختلال‌ها پایدار می‌ماند و می‌تواند از failureهای موقت عبور کند.
- `Hardware Fault` — خرابی در componentهای سخت‌افزاری مانند disk، RAM، network یا machine.
- `Software Error` — bug یا رفتار نادرست داخلی software که ممکن است در چند node تکرار شود.
- `Systematic Error` — faultی وابسته به یک علت مشترک یا الگوی تکرارشونده که چند node یا component را تحت تأثیر قرار می‌دهد.
- `Cascading Failure` — زنجیره‌ای که در آن fault یک component باعث fault در componentهای دیگر می‌شود.
- `Mean Time to Failure (MTTF)` — میانگین زمان مورد انتظار تا خرابی یک component.
- `Redundancy` — داشتن component یا مسیر جایگزین برای ادامهٔ service هنگام خرابی.
- `High Availability` — هدف حفظ دسترسی مداوم service و کاهش downtime هنگام maintenance یا failure.
- `Rolling Upgrade` — ارتقای تدریجی nodeها بدون توقف کل سیستم.
- `Process Isolation` — جدا کردن processها تا خطا یا مصرف resource یکی، دیگران را از کار نیندازد.
- `Configuration Error` — خطای ناشی از تنظیمات نادرست که می‌تواند باعث outage شود.
- `Sandbox` — محیط جدا و امن برای آزمایش بدون اثرگذاری بر کاربران production.
- `Automated Testing` — اجرای خودکار testها برای کشف bugها و پوشش corner caseها.
- `Rollback` — بازگرداندن تغییر به version یا configuration قبلی برای recovery سریع.
- `Monitoring` — جمع‌آوری metricها و signalها برای تشخیص زودهنگام مشکل و تحلیل failure.
- `Telemetry` — دادهٔ عملیاتی مانند metric، log و signal برای مشاهدهٔ رفتار سیستم.
- `Error Rate` — تعداد errorها نسبت به کل عملیات یا requestها در یک بازهٔ زمانی.
- `Backup` — نسخهٔ ذخیره‌شده‌ای که برای restore داده پس از corruption یا failure استفاده می‌شود.
- `Recovery` — اقدام‌ها و ابزارهای بازگرداندن سیستم یا داده به وضعیت قابل استفاده پس از failure.
- `Failure Detection` — پایش health componentها برای تشخیص سریع failure و آغاز recovery.
