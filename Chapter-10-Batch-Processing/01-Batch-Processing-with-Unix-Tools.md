# Chapter 10 — Batch Processing

## Batch Processing with Unix Tools

### Simple Log Analysis

فرض کنید web server هر بار که requestای را پاسخ می‌دهد، یک خط به log file اضافه می‌کند. برای مثال، با قالب پیش‌فرض access log در nginx، یک خط log ممکن است چنین باشد:

```text
216.58.210.78 - - [27/Feb/2015:17:55:11 +0000] "GET /css/typography.css HTTP/1.1" 200 3377 "http://martin.kleppmann.com/" "Mozilla/5.0 (Macintosh; Intel Mac OS X 10_9_5) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/40.0.2214.115 Safari/537.36"
```

این در اصل یک خط است و فقط برای خوانایی در کتاب به چند خط شکسته شده. برای تفسیرش باید تعریف قالب log را بدانیم:

```text
$remote_addr - $remote_user [$time_local] "$request"
$status $body_bytes_sent "$http_referer" "$http_user_agent"
```

این خط نشان می‌دهد server در ۲۷ فوریهٔ ۲۰۱۵، ساعت ۱۷:۵۵:۱۱ به وقت UTC، از client با IP برابر `216.58.210.78` درخواستی برای فایل `/css/typography.css` دریافت کرده است. user احراز هویت نشده، پس `$remote_user` با خط تیره (`-`) مشخص شده. status پاسخ `200` است، یعنی request موفق بوده، و حجم response برابر ۳۳۷۷ byte است. مرورگر Chrome 40 بوده و فایل را به‌دلیل ارجاع صفحه‌ای با URL برابر `http://martin.kleppmann.com/` بارگذاری کرده است.

ابزارهای مختلف می‌توانند از log file گزارش‌های جذابی دربارهٔ ترافیک وب‌سایت بسازند؛ اما برای تمرین، تحلیل را با ابزارهای سادهٔ Unix انجام دهیم. مثلاً برای پیدا کردن پنج صفحهٔ پرمراجعه می‌توان در shell نوشت:

```sh
cat /var/log/nginx/access.log |
  awk '{print $7}' |
  sort             |
  uniq -c          |
  sort -r -n       |
  head -n 5
```

این pipeline را می‌توان مرحله‌به‌مرحله خواند:

1. فایل log را بخوان.
2. هر خط را بر اساس whitespace به fieldها تقسیم کن و فقط field هفتم را چاپ کن؛ این field همان URL درخواستی است. در خط نمونه، URL برابر `/css/typography.css` است.
3. URLهای درخواست‌شده را به‌ترتیب الفبایی مرتب کن. اگر URLای `n` بار درخواست شده باشد، پس از sort همان URL `n` بار پشت‌سرهم دیده می‌شود.
4. دستور `uniq` خط‌های تکراری را با بررسی همسایه‌هایشان فیلتر می‌کند. گزینهٔ `-c` می‌گوید برای هر URL یکتا، تعداد دفعات تکرارش را هم چاپ کند.
5. `sort` دوم بر اساس عدد ابتدای هر خط (`-n`) مرتب می‌کند؛ این عدد شمار درخواست‌های URL است. گزینهٔ `-r` ترتیب را معکوس می‌کند تا تعداد بزرگ‌تر اول بیاید.
6. در پایان `head` فقط پنج خط نخست (`-n 5`) را نگه می‌دارد و بقیه را کنار می‌گذارد.

برای واضح‌بودن pipeline، بعضی‌ها یادآوری می‌کنند که `cat` ضروری نیست و می‌توان نام فایل را مستقیماً به‌عنوان argument به `awk` داد. بااین‌حال، شکل زنجیره‌ای pipeline در این مثال آشکارتر است.

خروجی این فرمان‌ها چیزی شبیه این است:

```text
4189 /favicon.ico
3631 /2013/05/24/improving-security-of-ssh-private-keys.html
2124 /2012/12/05/schema-evolution-in-avro-protocol-buffers-thrift.html
1369 /
 915 /css/typography.css
```

اگر با ابزارهای Unix آشنا نباشید شاید این command line کمی مبهم به‌نظر برسد، اما بسیار قدرتمند است: در چند ثانیه gigabyteها log را پردازش می‌کند و تغییر تحلیل هم آسان است. برای حذف فایل‌های CSS از گزارش، argument مربوط به `awk` را به `'$7 !~ /\.css$/ {print $7}'` تغییر دهید. برای شمردن IP addressهای client به‌جای صفحه‌های پربازدید، از `'{print $1}'` استفاده کنید.

در اینجا فرصت بررسی جزئی ابزارهای Unix را نداریم، اما یادگرفتنشان ارزشمند است. تحلیل‌های زیادی را می‌توان در چند دقیقه با ترکیبی از `awk`، `sed`، `grep`، `sort`، `uniq` و `xargs` انجام داد؛ عملکرد این ابزارها هم معمولاً فراتر از انتظار است.

#### زنجیرهٔ commandها در برابر برنامهٔ اختصاصی

به‌جای زنجیرهٔ commandهای Unix می‌توان برنامهٔ ساده‌ای نوشت که همین کار را انجام دهد. برای مثال، نسخه‌ای با Ruby می‌تواند چنین باشد:

```ruby
counts = Hash.new(0)

File.open('/var/log/nginx/access.log') do |file|
  file.each do |line|
    url = line.split[6]
    counts[url] += 1
  end
end

top5 = counts.map{|url, count| [count, url] }.sort.reverse[0...5]
top5.each{|count, url| puts "#{count} #{url}" }
```

- `counts` یک hash table است که تعداد دفعات مشاهدهٔ هر URL را نگه می‌دارد. مقدار اولیهٔ هر counter صفر است.
- از هر خط log، URL را از field هفتمِ جداشده با whitespace می‌گیریم. index آرایه در اینجا `6` است، چون آرایه‌های Ruby از صفر index می‌شوند.
- counter مربوط به URL خط فعلی را افزایش می‌دهیم.
- محتوای hash table را بر اساس counter به‌شکل نزولی sort می‌کنیم و پنج مورد اول را برمی‌داریم.
- آن پنج مورد را چاپ می‌کنیم.

این برنامه به‌اندازهٔ زنجیرهٔ Unix pipeها کوتاه نیست، اما خوانایی خوبی دارد؛ اینکه کدام‌یک را ترجیح دهید تا حدی سلیقه‌ای است. بااین‌حال، فراتر از تفاوت ظاهری syntax، جریان اجرای این دو روش تفاوت مهمی دارد که هنگام تحلیل file بزرگ آشکار می‌شود.

#### Sort کردن در برابر aggregation در memory

اسکریپت Ruby یک hash table در memory نگه می‌دارد که هر URL را به تعداد دفعات مشاهده‌اش map می‌کند. مثال Unix pipeline چنین hash tableای ندارد؛ در عوض فهرستی از URLها را sort می‌کند که در آن تکرار هر URL به‌شکل چند خط یکسان آمده است.

کدام روش بهتر است؟ به تعداد URLهای متفاوت بستگی دارد. در بیشتر وب‌سایت‌های کوچک و متوسط، احتمالاً تمام URLهای متمایز و counter هرکدام در مثلاً ۱ GB memory جا می‌شوند. **Working set** این job—مقدار memoryای که job برای دسترسی تصادفی نیاز دارد—فقط به تعداد URLهای متمایز وابسته است: حتی اگر یک URL یک میلیون بار در log آمده باشد، در hash table فقط به فضای یک URL و یک counter نیاز داریم. اگر working set به‌اندازهٔ کافی کوچک باشد، hash table داخل memory حتی روی laptop هم خوب کار می‌کند.

اما اگر working set از memory موجود بزرگ‌تر باشد، روش sort از disk کارآمدتر استفاده می‌کند. همان ایده‌ای است که در SSTable و LSM-Tree دیدیم: بخش‌هایی از data در memory sort و به‌شکل segment file روی disk نوشته می‌شوند، سپس چند segment مرتب در یک file بزرگ‌تر merge می‌شوند. Mergesort الگوی دسترسی sequential دارد و برای disk مناسب است. بهینه‌سازی sequential I/O در فصل ۳ هم یکی از موضوع‌های تکرارشونده بود؛ اینجا همان الگو دوباره ظاهر می‌شود.

ابزار `sort` در GNU Coreutils (Linux) به‌طور خودکار datasetهای بزرگ‌تر از memory را مدیریت می‌کند: بخش‌هایی از data را موقتاً روی disk می‌ریزد و sort را میان چند CPU core موازی می‌کند. بنابراین زنجیرهٔ سادهٔ commandهای Unix می‌تواند روی datasetهای بزرگ هم scale شود، بی‌آنکه memory تمام شود. احتمالاً bottleneck سرعت خواندن فایل ورودی از disk خواهد بود.

### The Unix Philosophy

اینکه توانستیم log file را به‌سادگی با زنجیره‌ای از commandها تحلیل کنیم اتفاقی نیست؛ این یکی از ایده‌های اصلی طراحی Unix بود و هنوز هم شگفت‌انگیز و مرتبط است. نگاهی دقیق‌تر به آن کمک می‌کند از ایده‌های Unix برای systemهای بزرگ‌مقیاس و ناهمگون استفاده کنیم.

Doug McIlroy، سازندهٔ Unix pipeها، در سال ۱۹۶۴ این ایده را به شلنگ باغچه تشبیه کرد: باید بتوان برنامه‌ها را به هم وصل کرد و هر وقت لازم شد برای تغییر شکل data، بخش دیگری به مسیر افزود. تشبیه plumbing ماندگار شد و اتصال programها با pipeها بخشی از چیزی شد که امروزه **Unix Philosophy** می‌نامیم؛ مجموعه‌ای از اصول طراحی که میان developerها و userهای Unix محبوب شد. در سال ۱۹۷۸ این اصول چنین توصیف شدند:

1. هر برنامه یک کار را خوب انجام دهد. برای کار تازه، برنامه‌ای تازه بسازید؛ برنامه‌های قدیمی را با featureهای بیشتر پیچیده نکنید.
2. فرض کنید خروجی هر برنامه ممکن است ورودی برنامه‌ای دیگر—حتی برنامه‌ای که هنوز نمی‌شناسید—شود. خروجی را با اطلاعات اضافی شلوغ نکنید. از قالب‌های ورودی سفت‌وسختِ ستونی یا binary پرهیز کنید و ورودی تعاملی را الزامی ندانید.
3. Software، حتی operating system، را طوری طراحی و بسازید که زود و ترجیحاً طی چند هفته قابل‌آزمایش باشد. از دور انداختن بخش‌های دست‌وپاگیر و بازسازی آن‌ها نترسید.
4. برای سبک‌کردن کار برنامه‌نویسی، به‌جای کمک غیرمتخصص از ابزار استفاده کنید؛ حتی اگر لازم باشد اول ابزارهایی بسازید و انتظار داشته باشید پس از پایان کار بعضی را کنار بگذارید.

این رویکرد—automation، prototyping سریع، iteration تدریجی، استقبال از آزمایش و تقسیم پروژه‌های بزرگ به بخش‌های قابل‌مدیریت—به جنبش‌های Agile و DevOps امروزی شباهت زیادی دارد. با گذشت چهار دهه، در این زمینه‌ها تغییر چندانی نکرده است.

ابزار `sort` نمونهٔ خوبی از برنامه‌ای است که یک کار را خوب انجام می‌دهد. حتی می‌توان گفت پیاده‌سازی sort آن از بیشتر پیاده‌سازی‌های libraryهای استاندارد زبان‌های برنامه‌نویسی بهتر است؛ چون آن‌ها معمولاً data را روی disk spill نمی‌کنند و از چند thread استفاده نمی‌کنند، حتی وقتی این کار مفید باشد. بااین‌حال `sort` به‌تنهایی کاربرد محدودی دارد و در ترکیب با ابزارهای Unix دیگر، مانند `uniq`، قدرتمند می‌شود.

Unix shell مانند bash اجازه می‌دهد این برنامه‌های کوچک را به‌سادگی compose کنیم و jobهای قدرتمند data processing بسازیم. با اینکه ممکن است این برنامه‌ها را گروه‌های مختلفی نوشته باشند، می‌توان آن‌ها را به‌شکل انعطاف‌پذیری به هم وصل کرد. Unix چطور چنین composabilityای را ممکن می‌کند؟

#### Interface یکنواخت

اگر انتظار داریم خروجی یک برنامه ورودی برنامهٔ دیگری شود، آن‌ها باید data format یکسان یا interface سازگار داشته باشند. برای اتصال خروجی هر برنامه به ورودی هر برنامهٔ دیگر، همهٔ برنامه‌ها باید از interface ورودی/خروجی مشترکی استفاده کنند. در Unix این interface یک file است؛ یا دقیق‌تر، **file descriptor**. File دنباله‌ای مرتب از byteهاست.

این interface ساده امکان نمایش چیزهای متنوعی را فراهم می‌کند: file واقعی در filesystem، channel ارتباطی با process دیگر (Unix socket، `stdin` و `stdout`)، device driver مانند `/dev/audio` یا `/dev/lp0`، یا socket مربوط به TCP connection. شاید عادی به‌نظر برسد، اما اشتراک یک interface یکنواخت میان این چیزهای متفاوت، اتصال و ترکیب آن‌ها را ممکن می‌کند.

طبق قرارداد، بسیاری از برنامه‌های Unix—نه همهٔ آن‌ها—این دنبالهٔ byte را متن ASCII در نظر می‌گیرند. در مثال تحلیل log، `awk`، `sort`، `uniq` و `head` فایل ورودی را مجموعه‌ای از recordها می‌بینند که با کاراکتر `\n` (newline، یعنی ASCII `0x0A`) از هم جدا شده‌اند. انتخاب `\n` قراردادی است؛ شاید جداکنندهٔ record در ASCII با مقدار `0x1E` انتخاب مناسب‌تری بود، اما یکسان‌بودن جداکننده میان این برنامه‌ها امکان همکاری آن‌ها را فراهم می‌کند.

تجزیهٔ هر record—یعنی هر خط ورودی—تعریف دقیق‌تری ندارد. ابزارهای Unix معمولاً خط را با whitespace یا tab به fieldها تقسیم می‌کنند؛ اما CSV، جداسازی با pipe و encodingهای دیگر هم به‌کار می‌روند. حتی ابزار ساده‌ای مثل `xargs` چندین command-line option برای تعیین روش parse کردن ورودی دارد.

interface یکنواخت مبتنی بر ASCII text در بیشتر مواقع جواب می‌دهد، اما بی‌نقص نیست: در مثال log از `{print $7}` برای استخراج URL استفاده کردیم که خوانایی چندانی ندارد. در حالت ایده‌آل چیزی مثل `{print $request_url}` مناسب‌تر بود؛ بعداً به این ایده برمی‌گردیم.

با وجود نقص‌ها، interface یکنواخت Unix حتی پس از چند دهه قابل‌توجه است. نرم‌افزارهای کمی به‌اندازهٔ ابزارهای Unix با هم interoperate و compose می‌شوند. به‌سادگی نمی‌توان محتوای email و تاریخچهٔ خرید آنلاین را از یک ابزار تحلیل سفارشی عبور داد، نتیجه را وارد spreadsheet کرد و در social network یا wiki منتشر کرد. امروز همکاری روان میان برنامه‌ها استثناست، نه قاعده.

حتی databaseهایی با data model یکسان هم انتقال آسان data از یکی به دیگری را فراهم نمی‌کنند. این نبود integration به **Balkanization of data** منجر می‌شود.

تشبیه interface یکنواخت را می‌توان در URL و HTTP، پایه‌های وب، هم دید: URL منبع مشخصی را در یک وب‌سایت شناسایی می‌کند و هر وب‌سایت دیگری می‌تواند به آن link دهد. Browser کاربر می‌تواند با دنبال‌کردن linkها میان سایت‌هایی با serverها و operatorهای کاملاً متفاوت جابه‌جا شود. این اصل امروز بدیهی است، اما از ایده‌های کلیدی موفقیت وب بود. در BBSهای قدیمی هر system شمارهٔ تلفن و تنظیمات baud rate مخصوص خودش را داشت؛ برای رفتن به BBS دیگر باید اتصال را قطع می‌کردید، شماره و تنظیمات modem را وارد می‌کردید و دستی دنبال محتوا می‌گشتید. امکان link مستقیم به محتوای داخل BBS دیگر وجود نداشت.

#### جدایی logic از wiring

ویژگی دیگر ابزارهای Unix استفاده از standard input (`stdin`) و standard output (`stdout`) است. اگر برنامه را بدون تنظیم دیگری اجرا کنید، `stdin` از keyboard می‌آید و `stdout` به screen می‌رود. اما می‌توان ورودی را از file گرفت یا خروجی را به file redirect کرد. Pipe، `stdout` یک process را با `stdin` process دیگر متصل می‌کند؛ این کار با buffer کوچکی در memory انجام می‌شود و لازم نیست کل stream میانی روی disk نوشته شود.

برنامه در صورت نیاز می‌تواند مستقیماً file بخواند یا بنویسد، اما روش Unix زمانی بهتر جواب می‌دهد که برنامه به path خاصی وابسته نباشد و فقط از `stdin` و `stdout` استفاده کند. در این صورت user در shell می‌تواند ورودی و خروجی را به هر شکل دلخواه wire کند؛ خود برنامه لازم نیست بداند ورودی از کجا می‌آید یا خروجی به کجا می‌رود. می‌توان این را نوعی loose coupling، late binding یا inversion of control دانست. جداسازی wiring ورودی/خروجی از logic برنامه، ترکیب ابزارهای کوچک در systemهای بزرگ‌تر را آسان می‌کند.

می‌توانید برنامهٔ خودتان را بنویسید و با ابزارهای operating system ترکیب کنید؛ کافی است از `stdin` بخواند و روی `stdout` بنویسد تا عضوی از data processing pipeline شود. در مثال log می‌توانید ابزاری بسازید که رشته‌های user-agent را به browser identifierهای قابل‌فهم‌تر تبدیل کند یا IP addressها را به country code نگاشت کند و آن را به pipeline وصل کنید. برای `sort` تفاوتی نمی‌کند با بخش دیگری از operating system ارتباط دارد یا با برنامه‌ای که شما نوشته‌اید.

بااین‌حال `stdin` و `stdout` محدودیت‌هایی دارند. برنامه‌های چندورودی یا چندخروجی ممکن‌اند اما کار با آن‌ها دشوار است. نمی‌توان خروجی برنامه را مستقیماً به network connection pipe کرد؛ مگر با ابزار جداگانه‌ای مانند `netcat` یا `curl`. اگر برنامه مستقیماً file باز کند، subprocess اجرا کند یا network connection برقرار کند، wiring آن I/O را خود برنامه انجام می‌دهد. این رفتار را می‌توان با command-line optionها configurable کرد، اما انعطاف shell برای سیم‌کشی ورودی و خروجی کمتر می‌شود.

#### شفافیت و آزمایش

یکی از دلایل موفقیت ابزارهای Unix این است که دیدن جریان کار را آسان می‌کنند:

- فایل‌های ورودی commandهای Unix معمولاً immutable در نظر گرفته می‌شوند. بنابراین می‌توانید command را بارها با optionهای مختلف اجرا کنید، بی‌آنکه فایل ورودی آسیب ببیند.
- می‌توانید pipeline را در هر مرحله متوقف کنید، خروجی را به `less` pipe کنید و ببینید شکل مورد انتظار را دارد یا نه. این امکان برای debugging مفید است.
- می‌توانید خروجی یک مرحله از pipeline را در file بنویسید و آن file را ورودی مرحلهٔ بعد قرار دهید. به این ترتیب مرحلهٔ بعد را دوباره اجرا می‌کنید، بی‌آنکه کل pipeline را از ابتدا اجرا کنید.

پس با اینکه ابزارهای Unix در مقایسه با query optimizer یک relational database ساده و کم‌ظرافت‌اند، به‌ویژه برای آزمایش همچنان بسیار کاربردی هستند. بزرگ‌ترین محدودیتشان این است که فقط روی یک machine اجرا می‌شوند؛ اینجاست که ابزارهایی مانند Hadoop وارد می‌شوند.

## Key Terms

- `Unix Pipeline` — زنجیره‌ای از commandها که خروجی هر مرحله را به ورودی مرحلهٔ بعد وصل می‌کند و jobهای data processing را از ابزارهای کوچک می‌سازد.
- `Unix Philosophy` — مجموعه‌ای از اصول طراحی Unix، از جمله اینکه هر برنامه یک کار را خوب انجام دهد و برنامه‌ها از طریق interface مشترک ترکیب‌پذیر باشند.
- `Working Set` — مجموعهٔ dataای که یک job برای اجرا به آن دسترسی فعال دارد؛ اندازه‌اش مشخص می‌کند aggregation در memory مناسب است یا باید از disk استفاده کرد.
- `External Sorting` — مرتب‌سازی dataset بزرگ‌تر از memory با مرتب‌کردن chunkها روی disk و merge کردن آن‌ها.
- `Sequential I/O` — خواندن یا نوشتن پیوستهٔ data که برای disk کارآمدتر از دسترسی تصادفی است.
- `File Descriptor` — شناسه‌ای برای دسترسی process به file یا منبع I/O بازشده؛ interface یکنواخت Unix برای file، pipe و socket.
- `Standard Input (stdin)` — stream ورودی پیش‌فرض process که shell می‌تواند آن را از keyboard، file یا pipe تأمین کند.
- `Standard Output (stdout)` — stream خروجی پیش‌فرض process که shell می‌تواند آن را به file هدایت یا به pipe متصل کند.
- `Composability` — قابلیت ترکیب componentهای مستقل از طریق interfaceهای سازگار برای ساخت pipelineها و systemهای بزرگ‌تر.
